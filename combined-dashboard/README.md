# BCore Performance Dashboard

Local Python tool that reads a Revenue/Gross Margin workbook and/or a
billable-utilization workbook and generates a single, fully self-contained
HTML dashboard. No internet, no CDN, no paid API — runs entirely offline.
Either input is optional; the dashboard renders whichever dataset(s) you
provide. An optional AI commentary panel narrates trends via a locally
installed `claude` CLI (see below); with no CLI installed, the dashboard
still builds normally and the panel is simply omitted.

## Requirements

- **Python 3.13 or later** (`python --version` to check)
- Windows 10/11 (tested); macOS/Linux should work but are untested

## Quickstart (Windows)

Double-click **`start.bat`** in this folder. It will:
1. Check that Python 3.13+ is installed
2. Create a virtual environment (`venv/`) on first run and install all dependencies
3. Start the server and open your browser to `http://localhost:5003`

> If you prefer the command line, see the Manual Setup section below.

## Manual Setup

```
pip install -r requirements.txt
```

For running the test suite:

```
pip install -r requirements-dev.txt
pytest
```

## Usage

### Local web upload (recommended)

```
python serve.py
```

Opens `http://localhost:5003` in your browser — drag one or both workbooks in
and click Generate. Files are processed in memory and never written to disk.

To use a different port: `set PORT=5010 && python serve.py` (Windows) or
`PORT=5010 python serve.py` (macOS/Linux).

### Command line (batch)

```
# Both workbooks -> combined dashboard with a Revenue/GM tab and a Utilization tab
python analyze.py --gm path/to/gm_workbook.xlsx --util path/to/utilization_workbook.xlsx

# Either one alone -> that section renders directly, no top-level tabs
python analyze.py --gm path/to/gm_workbook.xlsx
python analyze.py --util path/to/utilization_workbook.xlsx

# No flags -> auto-discovers and classifies .xlsx files sitting in input/
python analyze.py
```

Output is written to `output/dashboard_YYYY-MM-DD.html`.

## Input workbooks

**Revenue/GM workbook** — any number of monthly "GM Report" sheets (sheet
name must contain "GM Report", or be exactly `Jan26` for January), one `AOP`
plan sheet (division names in a fixed column/row layout — see
`config.yaml`'s `gm.aop_layout`), and optional monthly "Compare" sheets.
Column names are matched via the alias list in `config.yaml`'s `gm.gm_aliases`
/ `gm.compare_aliases`, so header spelling/case/spacing variations are
tolerated.

**Utilization workbook** — 8 exact-named sheets (`Billable Ute`, `Export`,
`Lookups`, `Unique Employees`, `First Days Last Days`, `Current PTO
Balances`, `Portfolio Leads Proj Types`, `Discrepancies`). See
`src/loader.py` for the full schema.

Both loaders follow a warn-don't-crash philosophy: a missing sheet, a
misnamed month, or missing columns are recorded as issues (surfaced in the
Revenue/GM dashboard's "Workbook Scan" panel, or printed to the console for
utilization) rather than aborting the whole run.

## AI trend commentary (optional)

Each division tab (Revenue/GM) and each view (Utilization) can show a short
CFO-facing narrative — a headline, a risk level, 2-3 sentences of context,
and one recommended action — generated by piping already-computed numbers
to a locally installed [Claude Code CLI](https://code.claude.com/docs/en/quickstart.md)
in non-interactive mode (`claude -p`). It never uses the paid Anthropic API:
it reuses whatever account is already logged into `claude` on this machine.

**Setup** (one-time, only if you want this feature):
1. Install the CLI — `irm https://claude.ai/install.ps1 | iex` (PowerShell)
   or `winget install Anthropic.ClaudeCode`.
2. Run `claude` once and log in interactively.
3. Nothing else to configure — `config.yaml`'s `ai_commentary.enabled: true`
   (the default) picks it up automatically on the next `analyze.py`/`serve.py`
   run.

**To turn it off:** set `ai_commentary.enabled: false` in `config.yaml`.

**Data never leaves Python for the raw workbook.** The LLM only ever sees
small, already-aggregated JSON — a handful of monthly totals per division
(`src/forecaster.py::project_gm_series`, ~300-400 bytes per division) or a
capped list of the most severe trend flags plus division/portfolio rollups
per view (`src/forecaster.py::summarize_utilization_trends`, capped at
`ai_commentary.max_flags_per_view`, typically a few KB). A 13,000-row Export
sheet is fully parsed, classified, and aggregated by pandas/numpy in
`src/loader.py` → `src/calculator.py` → `src/view_builder.py` well before
`src/ai_commentary.py` runs — the LLM never sees a single raw row, so token
cost stays flat regardless of workbook size. Numeric forecasts (year-end
revenue/GM projection, variance vs. AOP) are plain `numpy.polyfit` linear
extrapolation in `src/forecaster.py`; the LLM only narrates numbers Python
already computed, never invents its own.

Results are cached on disk (`output/.ai_cache/<sha256 of payload>.json`), so
re-running on unchanged data does not re-invoke `claude`. Any failure
(CLI not installed, timeout, malformed response) is caught and the panel is
silently omitted — it never blocks the dashboard from building.

## Structured data store & cross-dataset flagging

Every run also writes per-period rollups to a local SQLite database
(`data/bcore.db`, via `src/store.py`) — separate from `output/history/`'s
rendered-HTML archive. This is what powers:

- **Duplicate-upload detection**: re-uploading a workbook that overlaps
  periods/months already ingested triggers a confirmation step in
  `serve.py` ("N period(s) already ingested — confirm to overwrite, or
  cancel") before anything is committed. The CLI (`analyze.py`) has no
  confirm-click UI, so it just logs a warning and overwrites.
- **Cross-dataset flagging** (`src/cross_flagger.py`): flags any division
  that's low on **both** utilization (below `cross_flags.utilization_target`,
  default 85%) and revenue-vs-AOP variance — this combination is surfaced as
  `critical` (red), a single-metric or MTD-only miss as `warning` (amber).
  Reads the *persisted* state in `data/bcore.db`, not just the current
  upload's rows, so GM and utilization workbooks uploaded in separate
  sessions still combine correctly. Shown as a "Division Health" tab
  whenever both a GM and a utilization workbook are rendered together.
  Note: the utilization tracker's division codes (`BL`/`IS`) don't match the
  GM workbook's (`BL1`/`IS1`) — confirmed against both real workbooks — so
  `config.yaml`'s `cross_flags.util_division_aliases` re-keys one onto the
  other before joining.
- **Insights export** (`src/insights_exporter.py`): a small, LLM-friendly
  summary written to `exports/insights_latest.json` after every run — see
  `skills/bcore-insights/SKILL.md` for the schema and how a Claude Skill
  should read it.

**Clear All Data** (landing page, type-to-confirm modal) deletes
`data/bcore.db` and `exports/insights_latest.json` only — `output/history/`
(your saved rendered dashboards) is untouched.

## Project structure

```
combined-dashboard/
  analyze.py                 CLI entry point
  serve.py                   Local Flask upload UI
  config.yaml                All thresholds, sheet names, column aliases
  create_sample_data.py       Utilization sample generator
  create_sample_gm_data.py    Revenue/GM sample generator
  requirements.txt / requirements-dev.txt
  input/  output/  data/  exports/
  skills/bcore-insights/SKILL.md   How a Claude Skill should read exports/insights_latest.json
  src/
    common.py                 Number/currency parsing, column-alias resolver, inline SVG chart helper
    loader.py, classifier.py, periodizer.py, calculator.py,
    trend_detector.py, aggregator.py, view_builder.py         Utilization pipeline
    gm_loader.py               Revenue/GM workbook parser
    gm_calculator.py           Revenue/GM KPI/chart/table aggregation
    forecaster.py              Linear GM projections + utilization trend summaries (pure Python/numpy)
    ai_commentary.py           Optional `claude` CLI subprocess wrapper — narrates forecaster.py's numbers
    store.py                   SQLite persistence (data/bcore.db) + period-collision detection
    cross_flagger.py           Combined utilization+revenue flagging logic (pure Python, no I/O)
    insights_exporter.py       Builds exports/insights_latest.json from cross_flagger.py's output
    renderer.py                 Combines both into one output file
  templates/
    gm_section.html.j2          Revenue & Gross Margin dashboard (standalone document)
    utilization_section.html.j2 Utilization dashboard (standalone document)
    dashboard.html.j2           Combined shell — tabs between the two, each embedded via <iframe srcdoc>
  tests/                        pytest suite covering both pipelines' calculation cores
```

The combined shell embeds each sub-dashboard as a fully independent
`<iframe srcdoc>` document rather than merging their HTML/CSS/JS into one
DOM — this guarantees neither side's styles or scripts can collide with the
other's, at zero cost to the "single self-contained HTML file" delivery
model.

## Utilization trend detection

Six trend types, flagged only when a condition persists for 3 consecutive
active periods by default (`persistence_threshold` in `config.yaml`):
low billable/direct utilization, excessive PTO, high B&P, high
non-billable project hours, and G&A crowding. Corporate-role employees
(≥80% G&A+Overhead, zero billable) are excluded from trend detection.
